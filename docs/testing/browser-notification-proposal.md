# 剩余浏览器与通知任务：待确认的实施决策

> 2026-10-06；**提案，尚未批准为实施规格**。此文保留全部剩余目标，不将现有离线测试视作真实浏览器、通知或生产验收完成。

## 权威依据与必须保留的目标

- [平台开发文档](../platform/agent-fleet-self-hosted-platform.md)：M3/M4 与 T3.6 剩余项目包含真实浏览器生命周期、观察界面、Take Control/Return Control、Browserbase、SecretBroker 和通知。
- [T3.7 网络规格](../superpowers/specs/2026-10-04-t3.7-browser-navigation-network-boundary.md) §1/§2/§3.6/§5：真实 driver 必须另行决策，并证明浏览器进程无法绕过网络限制；请求拦截、固定地址的 CONNECT 代理、操作系统网络限制三层均不可省略。不得引入 TLS 中间人。
- [提交审批规格](../superpowers/specs/2026-10-05-browser-submit-approval-contract.md)：提交必须由同一 Run/session/selector 的单次授权控制；普通输入或接管不能绕过授权。
- [外部验收契约](release-acceptance.md)：真实模型、邮件、节点、部署、备份/回滚各自需要环境证据。

当前已存在 `LocalBrowserBackend` 的注入 driver 契约、签名命令和 journal、`BrowserRepository` 的会话/产物/审批持久化、ExecutionWindow 的连接/单写入租约，以及账号邮件适配器。复用这些边界；不建立另一条 Node 传输、通用工作流引擎或任意脚本入口。

## 决策 A：真实浏览器的执行环境

**建议先在专用 Linux 测试 Node 上完成真实 Chromium 的全过程证明。** 本机为 Darwin；当前 PATH 未发现 Docker、Podman 或 bubblewrap。现有 Chrome 浏览器 UI 测试可以验证页面行为，不能证明 Linux 进程网络隔离。不得为本任务擅自安装特权组件或改宿主机防火墙。

批准这一方向前需要明确测试 Node/可用的隔离运行环境。依赖和 Chromium 版本应在该环境中固定；项目尚无生产浏览器 driver 依赖，不把临时 Playwright 测试目录作为生产运行时。

必须交付的实际证明：

1. 浏览器只能连接 Node 自己管理的 egress adapter；直接 IPv4/IPv6、UDP、DNS、代理/PAC、QUIC、WebRTC、WebSocket 和扩展绕过均无法建立连接。
2. CONNECT 仅连接同一次已验证解析中的固定地址；TLS 由浏览器与目标端到端完成，证书验证不关闭。代理不能被任意本机进程作为开放代理使用。
3. Chromium 的原生请求/响应拦截覆盖导航、重定向、iframe、脚本、fetch、worker 等；在转发超额数据前执行现有方法、头部、解压后正文和会话总量限制。实现前先验证所选 Chromium API 确实支持有界读取和背压，不能用事后读取完整 body 代替。
4. 任意一层不可用时 driver 不暴露可执行 capability；不得回退到原生直连、修改限额或仅检查初始 URL。
5. 驱动崩溃、Node 重启、注册失败、Run 结束和凭据撤销后，受管进程/临时 profile/连接确定关闭；按进程实例身份回收，不能仅凭可能复用的 PID 杀进程。已 dispatch 的不确定命令保持 `unknown`，不得重放。

数据结构保持现有 session_id 哈希索引；准入/租约变化使用短 SQLite 事务，进程与网络操作在事务外执行。命令/帧有界，清理与所属 Node 生命周期绑定。

## 决策 B：观察、接管与浏览器凭据

**建议按“观察 → 接管 → 凭据 → Browserbase”依次完成，每一项都有独立验收，后项不因前项完成而关闭。**

观察建议：复用现有截图产物通路与同源权限检查；帧不进入模型文本、journal 或普通事件。建议先采用单个最新帧、有背压的拉取模式，频率上限 1 帧/秒，单帧继续使用现有 256 KiB PNG 上限。这些频率/保留策略是待确认的新产品参数。页面隐藏/关闭立即停止读取；重新打开根据持久化 session/window 状态恢复。过期、撤销和跨 owner/run 的内容一律不可取。

接管建议：浏览器输入命令绑定现有 ExecutionWindow 的持有者、epoch 和 session；Node 在真正输入前复验。获取人工 writer 时，原 agent writer 的旧 epoch 立即无效；归还或到期也产生新 epoch。UI 必须明确只读、等待、人工控制、已归还/过期状态；不能把页面本地状态当作租约。过期与新输入竞态、双窗口竞争、断线恢复和撤销必须使用真实 driver 验证。`submit` 仍经过单次审批，不随接管自动获准。

凭据与 Browserbase 需要分别确认目标账号/供应商环境与允许的域名、数据保留和费用范围。当前 T3.7 禁止 Cookie/Authorization 等凭据流入；不得仅因存在 SecretBroker 就解除该规则。必须先形成凭据上下文的新契约，明确只在受控 Node 解密、域名绑定、会话销毁、撤销和审计。Browserbase 必须提供并验收等价的网络与数据隔离能力；供应商返回成功或可创建 session 不是等价证明。

## 决策 C：通知触发与渠道

平台只写明“Notifications”，现有事件和账号邮件不能决定通知业务规则。以下是建议的第一版，**需要产品确认后才写运行代码**：

| 项目 | 建议 | 对交付的影响 |
|---|---|---|
| 初始触发 | Run failed/unknown、待审批操作、Incident 新开/恢复 | 固定事件来源；不根据模型正文推断通知 |
| 默认渠道 | 站内通知；逐渠道显式启用外发 | 不沿用账号验证码收件人作为业务订阅人 |
| 成功通知 | 默认关闭，用户显式选择 | 避免每次成功产生大量提醒 |
| 聚合/幂等 | 同 owner + source event + channel 唯一 | 重启/重复事件不能重复创建站内提醒 |
| 建议保留 | 站内 30 天、列表每页至多 100 条 | 属于待确认的新参数，不改现有审计保留 |
| 外发候选 | 复用已有 SMTP/one-mail 传输边界 | 必须指定收件人、触发范围和外发授权；其他渠道另定契约 |

确认后应实现：强类型通知 DTO、owner 与源对象权限复验、事务内事件/outbox 写入、短租约派送、读取/已读/归档状态、渠道启停、幂等和有界失败回执。正文使用固定模板和可授权的对象链接，不携带提示词、日志、文件内容、Cookie、secret_ref 或原始异常。外发结果不确定时保留 `unknown`，不自动重放可能已经送达的消息。站内事务失败回滚与外部投递失败是不同状态。

UI 需要成功、空、加载、失败、重复事件、撤销权限和窄屏验收。真实邮箱送达必须有独立收件证据；本任务在批准渠道、对象和接收方前不发业务消息。

## 验收与实施顺序

| 顺序 | 可交付内容 | 完成证据 |
|---|---|---|
| 1 | 确认 A 的测试环境与 driver/隔离实现选择 | 固定版本与实际 Linux 运行环境；三层网络 PoC 通过 |
| 2 | 真实浏览器生命周期与现有固定工具 | 真实 Node/Chromium、关闭/崩溃/超时/撤销、无泄漏/无重放 |
| 3 | 观察与接管 | 真实帧、权限隔离、背压、双 writer 和到期竞态，浏览器端 UI 流程 |
| 4 | 凭据与 Browserbase 的专项契约和实现 | 每个实际环境的隔离、凭据、撤销、费用与数据范围证明 |
| 5 | 确认 C 后实现通知 | 本地事务/幂等/权限/重启测试，指定渠道的真实送达验收 |
| 6 | 全项目收口 | 完整需求映射、全部本地流程、Linux 条件测试、最终提交打包，以及各项外部验收 |

以上顺序不删除或豁免任何原始目标。已提交的结果摘要、调度、journal 和输出限额修复可以独立合并；它们不使这份提案或剩余产品能力自动成为已完成。
