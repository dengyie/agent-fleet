# T3.7 Browser Navigation Network Boundary Specification

> Status: approved for the offline policy/pinned-transport contract only; implemented in part. T3.6 remains the only browser runtime slice. External browser networking and real-browser integration remain blocked because process-level socket enforcement is not proven. This document authorizes no gate change, external network access, production credential use, or deployment.

## 1. Goal

Harden the existing T3.6 browser Node contract so an enabled browser session cannot reach an unapproved network destination through a top-level navigation, redirect, frame, script, image, stylesheet, fetch/XHR, worker, or other browser-originated HTTP(S) request. Validate every request and bind the connection to the exact IP socket address that passed policy. Keep the Hub/Node outbound command transport and T3.6 artifact/session contracts unchanged.

This is a network-boundary slice, not a production browser integration. A real Chromium/Playwright driver, production enablement, and external endpoint pilot are separate work with separate approval and acceptance.

## 2. Baseline and compatibility

- Preserve T3.6 gates: `platform_browser_enabled` and `platform_browser_network_enabled` remain default-off and retain parent-gate behavior.
- Preserve fixed browser capability/tool allowlists, bounded arguments/results, opaque session scope, manual-only command retry, and artifact redaction. T3.7 does not load a user's browser profile or import cookies, authentication state, client certificates, or credentials. Browser-managed cookie persistence, HTTP authentication caches, client certificates, and credential prompts are disabled; `Cookie`, `Set-Cookie`, `Authorization`, and `Proxy-Authorization` are stripped/rejected at the egress boundary. Credential-bearing browser contexts are unavailable.
- Loopback remains available only for disposable local fixtures under the existing test/local policy. It is not an external-network exception and must not be widened by this slice.
- Apply the same outbound destination policy to `browser.open` and every later `browser.navigate`; policy is also enforced on all requests generated by the page, not only tool-supplied URLs.
- Hub admission may reject an invalid initial URL early, but Node/runtime enforcement is authoritative because redirects and subresources happen after admission.
- No new third-party dependency is required. The required enforcement topology has three non-substitutable layers: (1) a browser-native request/response interceptor validates each navigation, redirect, subresource, method, headers, response headers, and decoded body budget; (2) a per-Node owned egress adapter is the browser's only configured proxy, resolves/validates each CONNECT destination, and pins its outbound TCP connection; HTTPS uses CONNECT pass-through so TLS remains end-to-end; (3) OS/container egress policy prevents the browser process from opening direct network sockets or bypassing the adapter. Ambient proxy settings are ignored. If any layer cannot be enforced, external navigation is unavailable; native unrestricted browser networking is forbidden.

## 3. Policy model

### 3.1 URL and origin

For every HTTP(S) request:

- The test-only loopback fixture override is injected at the transport boundary and is not configurable through Hub, Node manifests, user input, or production config. A test hostname may resolve to loopback only under that explicit fixture override; the external-origin policy always rejects loopback answers.

- Parse and normalize the URL with one shared policy implementation. Reject malformed URLs, unsupported schemes, userinfo, control characters, invalid ports, empty hostnames, and URL forms whose authority is ambiguous.
- Match the normalized origin (`scheme`, IDNA-normalized lowercase hostname without a trailing dot, and effective port; normalize explicit default ports to the scheme default) against the exact configured origin allowlist. The allowlist parser must apply the same normalization at configuration load and request time; malformed or duplicate-normalized entries fail closed. Do not use suffix, wildcard, substring, registrable-domain, or redirect inheritance matching.
- Require HTTPS for external origins. Plain HTTP is permitted only for loopback fixture URLs; all other HTTP requests fail closed.
- Reject IP literals unless they are loopback fixture addresses. Reject non-global destinations, including private, loopback, link-local, multicast, unspecified, reserved, IPv4-mapped private IPv6, and mixed public/private DNS answers.
- Preserve path and query as request data; fragments are never sent and do not affect network authorization.

### 3.2 DNS resolution and connect-address binding

- Resolve the request hostname once per new origin connection using an injectable resolver. The resolver returns a bounded, non-empty set of stream addresses for the effective port.
- Validate every returned address. If any answer is malformed, non-global, disallowed, or the result set exceeds the configured bound, deny the request; do not filter unsafe answers and continue with the remaining public answers.
- Normalize/deduplicate addresses without changing the validated socket address/port tuple. Bound address count (maximum 16 per resolution) and reject empty/truncated/unsupported resolver results.
- Connect directly to one of the validated socket addresses with the original effective port. No second hostname lookup, proxy-side DNS resolution, Happy Eyeballs re-resolution, retry through the hostname, or unpinned fallback is permitted.
- If the selected address fails to connect, the transport may try another address only from the same fully validated resolution result, under the same request deadline. It must never resolve again during that request/connection attempt.
- Cache pins only for the lifetime of a single origin connection. Every new connection, including reconnect after failure, performs a fresh resolution and complete validation. Do not keep a process-wide DNS cache or reuse a pin across origin/port changes.
- Do not trust `Host`, `:authority`, proxy environment variables, browser PAC settings, or caller-provided routing metadata to select the socket destination. The normalized authorized URL determines host and port.

### 3.3 Redirects

- Do not delegate redirects to the browser's unrestricted default redirect handler. Every redirect hop must pass through the same request gate and pinned transport as a new request.
- Permit at most 10 redirect responses for a single navigation/resource request; the 11th redirect is denied. Detect a repeated normalized `(method, URL)` in the chain and deny loops.
- Accept only HTTP redirect status codes 301, 302, 303, 307, and 308 with exactly one syntactically valid `Location` target. Reject missing, multiple, malformed, control-character, or unsupported-scheme targets.
- Resolve relative `Location` against the current response URL, then parse, normalize, origin-check, resolve, classify, and pin it independently. Same-origin redirects receive no exemption from DNS/IP checks. Cross-origin redirects require the destination's own exact allowlist entry and HTTPS policy.
- Never forward Authorization, Proxy-Authorization, Cookie, or other origin-bound credentials across an origin change. T3.7 does not add browser credentials; the transport must not synthesize or import them. Strip origin-bound headers on any origin change and reject credentials embedded in URLs.
- A rejected hop aborts that request and yields a bounded deterministic browser policy failure using only these stable codes: `redirect_denied`, `origin_forbidden`, `origin_unresolvable`, `network_disabled`, `invalid_url`, `response_invalid`, `response_too_large`, `request_limit_exceeded`, `protocol_forbidden`, `method_forbidden`, `tls_failed`, `timeout`, or `backend_unavailable`. No response body or raw Location value is included in receipt, log, journal, event, or model context.
- Since only GET and HEAD are allowed, redirects preserve the current method for 301/302/303/307/308. The implementation must not introduce POST rewriting or replay semantics.
- Redirect validation applies equally to top-level navigation and subresource requests. A blocked subresource must not disable the network gate or allow an alternate unrestricted load path.

### 3.4 TLS and proxy behavior

- For HTTPS, connect TCP directly to the pinned address, then perform normal certificate-chain and hostname verification against the original normalized DNS hostname. Send the original hostname as TLS SNI; do not use the IP literal as the verification identity for DNS URLs.
- For an HTTPS IP-literal fixture (loopback only), use the IP identity and normal certificate verification rules; tests may use a test CA/certificate, never disable verification.
- For external HTTPS through the per-Node egress adapter, use an HTTP CONNECT tunnel to the validated pinned address. The browser performs TLS directly through the tunnel, using the original hostname for SNI and normal CA/hostname verification. The adapter must not terminate TLS or inspect application headers/body.
- Do not install a local interception CA, rewrite page content, or expose plaintext application traffic to the Hub. No TLS MITM is part of this contract.
- Ignore ambient `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and PAC configuration. The browser transport is explicitly configured to use only the per-Node adapter; the adapter itself connects directly to validated socket addresses, not through an upstream proxy.
- Preserve standard TLS hostname verification and bounded connect/handshake/read timeouts. Certificate errors are deterministic bounded failures; they must not trigger HTTP downgrade, certificate bypass, alternate hostname, or unpinned retry.

### 3.5 Request methods, headers, and browser bypasses

- Permit only `GET` and `HEAD` for page-originated network requests in T3.7. Other methods fail closed; form submission and state-changing browser interaction require a later separately approved contract. This does not change the existing local `browser.click`/`browser.type` API, but any resulting network request other than GET/HEAD is blocked.
- Strip or reject caller-supplied `Host`, `:authority`, `Proxy-Authorization`, `Proxy-Connection`, hop-by-hop headers, and transport-routing headers. The adapter derives authority from the normalized URL. Requests may not set proxy authentication or select an upstream proxy.

### 3.6 Unsupported protocols and browser bypasses

- Deny non-HTTP(S) network schemes, including `file:`, `javascript:`, `ftp:`, `ws:`, and `wss:`. `about:blank` may be used only as an inert initial page and cannot inherit or create network authority. `data:` and `blob:` may be consumed only as non-network subresources created by the current document; they cannot be top-level navigation targets, workers, downloads, or a source of network authority. Exact driver enforcement must be proven in tests.
- Deny WebSocket, WebRTC/ICE/STUN/TURN, QUIC/HTTP3, browser extensions, service workers, downloads, and external protocol handlers in T3.7. These require separate reviewed contracts; there is no opt-in bypass in this slice.
- Block browser DNS prefetch, preconnect, speculative loading, and alternate-service/Alt-Svc connection paths unless each resulting socket is proven to use the approved pin. Do not allow HSTS or Alt-Svc to silently change the authorized origin/transport policy.
- Browser process networking must be restricted so the browser cannot open an unmanaged socket around the request gate. A driver callback alone is insufficient if the browser retains unrestricted egress. The implementation contract must provide enforceable process/network isolation or an equivalent browser transport that owns every socket. If that cannot be guaranteed on the target runtime, external network mode stays unavailable and the gate remains off.

## 4. Resource and error bounds

- Maximum redirects per request: 10.
- Maximum resolver addresses per request: 16.
- Each HTTP(S) request receives one absolute monotonic 20-second deadline covering DNS, connect attempts, TLS handshake, redirects, response headers, and body reads. Redirect hops and reconnect attempts share the original request deadline; they cannot reset it. This is below the existing default 30-second `RemoteToolBroker` receipt wait and 60-second Node lease. Resolver and socket APIs receive the remaining budget; if DNS cannot be bounded/cancelled within it, external networking is unavailable on that runtime.
- Enforce a per-session cap of 16 concurrent requests, a 64 KiB aggregate response-header limit, a 16 MiB body limit per request, and a 64 MiB aggregate transferred-response-body budget per browser session. Count bytes as streamed; abort before forwarding bytes that exceed a limit. Redirect response bodies are discarded and capped at 64 KiB before closing the response. These ceilings include failed/redirected responses and are not reset by navigation or redirect.
- Do not buffer unbounded response bodies in the policy layer. Preserve the browser's existing bounded snapshot/screenshot/result contract; deny oversized redirect headers and malformed response metadata with stable codes.
- Error codes are stable, secret-free, and contain no URL, hostname, IP, certificate detail, response header/body, or credential material. Use `response_too_large` for header/body/session byte limits and `request_limit_exceeded` for concurrency or resolver-answer count limits. Unexpected driver failure after dispatch retains T3.6 `unknown` semantics; deterministic policy/TLS denial is `failed`.

## 5. Proposed implementation boundary

- Domain/policy: extend the existing browser URL/origin policy with normalized request and redirect decisions; no Flask, SQLite, or browser-framework types.
- Infrastructure: one pinned HTTP(S) transport/request-gate adapter used by the actual driver for navigation and all page-generated HTTP(S) traffic. It owns DNS resolution, address classification, socket connect, TLS identity verification, redirects, and deadlines. Avoid a second generic network abstraction if one adapter satisfies the single driver boundary.
- Application/Node: construct the backend only when the existing gates and a driver that proves enforcement are present; otherwise manifest/admission stays unavailable and execution returns bounded `backend_unavailable`/policy errors.
- Hub admission: retain early validation for the initial requested URL only. Never treat Hub admission as proof that page requests are safe.
- Driver compatibility: injected fakes prove transport behavior. A real browser adapter is not silently introduced by this spec and requires a later implementation decision plus process-level egress proof.

## 6. Acceptance matrix

All current transport evidence is offline and deterministic. Most tests use injected resolver data, fake sockets/connections, and fake TLS contexts; the synthetic public IP is never contacted. A bounded local loopback TLS fixture additionally exercises a real TCP socket, real TLS handshake, test CA trust, DNS SAN hostname verification, original-host SNI, pinned loopback port, and stable rejection for an untrusted CA or hostname mismatch. No test contacts external DNS, the Internet, VPS, a production browser/profile, or production credentials. The direct transport seam is not connected to `NodeRuntime`.

### Positive cases

Status labels describe the current repository tests only: **Covered** means directly exercised by a deterministic local test; **Partial** means some mechanics are tested but the complete stated guarantee is not; **Blocked** means runtime behavior is absent and must not be claimed.

1. **Covered (offline seam):** exact HTTPS origin, shared canonical scheme/host/port normalization, synthetic global answer, pinned sockaddr, one DNS resolution per connection.
2. **Covered (offline seam):** same-origin redirect and per-hop resolution, including the exact ten-followed-hop / eleventh-response denial boundary and canonical-equivalent loop rejection before another request.
3. **Covered (offline seam):** allowlisted cross-origin redirect. Credential forwarding is constrained by the fixed request-header allowlist; origin-bound credential headers are rejected at input, and allowed headers are stripped on the cross-origin hop.
4. **Covered (offline seam):** relative redirect resolution, fragment removal, unsupported-scheme/overlong Location rejection, and preservation of GET/HEAD across supported redirect statuses.
5. **Covered (local TLS fixture):** a real loopback TCP/TLS exchange verifies a test CA and DNS SAN, asserts original-host SNI and the connected loopback port, and rejects both an untrusted CA and hostname mismatch with `tls_failed`. Production CA-chain, expiry, IP-identity, and browser TLS integration remain untested.
6. **Partial (offline seam):** synthetic resolver answers are used for external-address policy; there is no real DNS fixture, by design. The local TLS fixture resolves only to its bound loopback address.
7. **Partial:** transport errors are asserted to exclude the input URL, redirect Location, and response body. Stable errors and screenshot materialization have local journal/receipt coverage, but redirect URL/IP secrecy across every Run event, model boundary, and test log has not been asserted as one end-to-end property.

### Negative cases

1. **Covered (offline seam):** unsupported method, forbidden headers, malformed ports/authority (including explicit empty/zero port), multi-dot host suffix, missing host, malformed IPv6 authority, URL userinfo, and control characters are rejected. A shared normalizer enforces the same scheme/hostname/effective-port rules for policy admission, transport request URLs, and allowlist entries; duplicate normalized allowlist origins fail closed.
2. **Covered (representative offline classifications):** mixed public/private or public/loopback answers, RFC1918, link-local, multicast, unspecified, reserved IPv4, unique-local IPv6, mapped-private IPv6, malformed sockaddr, and resolver answer overflow are rejected. This is a representative classification matrix, not a claim of exhaustive registry enumeration.
3. **Partial (offline seam):** direct socket connect attempts use only validated sockaddr values; failed-address fallback stays within the current validated list without a resolver retry, and separate requests resolve independently. A system-level spy proving no later OS/browser/proxy hostname lookup is not present.
4. **Covered (offline seam):** redirect hops re-resolve independently; same-result connection fallback, failed-address cleanup, and request-to-request pin refresh are tested. This does not prove browser/OS-level socket behavior.
5. **Covered (offline seam):** redirect loops (including canonical-equivalent URLs), disallowed origins/schemes/targets, fragments, missing/multiple `Location`, malformed redirect authority, overlong/unsupported-scheme `Location`, and the eleventh redirect response are rejected before any forbidden follow-up request.
6. **Covered (offline seam):** forbidden credential/routing headers are rejected, response-sensitive headers are filtered, allowed headers remain on same-origin redirects and are stripped on cross-origin redirects.
7. **Covered (local TLS fixture) / Partial overall:** required TLS settings, SNI, timeout mapping, generic TLS failure mapping, untrusted-CA rejection, and hostname-mismatch rejection are tested locally. Certificate expiry, IP-identity, production CA-chain, and browser TLS integration remain untested.
8. **Blocked:** no browser process, proxy/PAC, Alt-Svc, WebSocket, WebRTC, QUIC, or unmanaged-socket enforcement is implemented or proven.
9. **Covered (offline seam):** method/header, response body/header/session budgets, redirect loops, fixed limit ceilings, and a contended 16-request cap are tested; the 17th concurrent request is rejected, and capacity is available again after completion. Duplicate request header names fail closed case-insensitively, response duplicate headers have a locked deterministic shape (case-insensitive sensitive filtering, exact-name overwrite, case variants kept), and the real bounded parser charges header lines against the exact aggregate boundary.
10. **Covered (offline seam):** bounded resolver timeout inputs, socket timeout handling, and absolute-deadline checks exist. Advancing-clock fixtures prove DNS, connect, TLS handshake, redirect hops, response-header reads, and response-body reads each hit the shared deadline and stop before any later phase. Real OS/socket scheduling beyond the injected seams is not proven (see case 3).
11. **Partial:** deterministic backend failures map to `failed`, and an after-dispatch driver failure maps through `NodeClient` to an `unknown` journal/receipt. Transport-level URL/IP/Location/body secrecy and Node journal/wire-receipt exclusion of URL/IP/body/TLS exception markers are directly asserted; full leak assertions over every Run event, model boundary, log, and artifact metadata remain incomplete.

### Exit criteria

- **Blocked:** prove every browser-originated network socket is created by the enforcing adapter or denied by process/network isolation. No such proof exists; external browser networking remains unavailable.
- **Blocked:** enforce every navigation, redirect, and page-generated subresource through the pinned transport. There is no browser-native interceptor or runtime wiring.
- **Partial:** preserve TLS verification configuration and SNI in the offline transport contract. A local test CA/DNS SAN fixture covers certificate trust and hostname mismatch on loopback; production certificate chains, expiry/IP identity, and browser TLS integration remain unverified.
- Treat only the specifically tested offline cases above as passing. The complete positive/negative matrix has not passed and must not be represented as complete.
- Compile/static checks and `git diff --check` must pass for the current implementation before this offline slice is considered verified.
- Browser/network production gates remain off. This contract authorizes neither external network access nor deployment.

## 7. Implementation entry gate

The policy decisions above are fixed for this slice; implementation must not weaken them. One runtime feasibility proof remains an entry gate, not permission to invent a weaker policy:

1. Before wiring a real browser driver, demonstrate on every supported deployment OS/container boundary that all browser-originated sockets are either created by the pinned adapter or denied by process/network isolation. A request interception callback alone does not satisfy this gate.
2. If that proof cannot be produced with the existing runtime and dependencies, implement/test only the isolated policy and pinned-transport contract, keep external browser networking and any real-browser backend unavailable, and report T3.7 runtime integration blocked. Do not add an OS-specific firewall, proxy service, dependency, deployment change, or production gate without a separately reviewed and approved design.
3. The 20-second monotonic request deadline, 10 redirect maximum, 16 DNS-answer maximum, 16 concurrent-request maximum, 64 KiB aggregate response-header limit, 16 MiB per-request body limit, 64 MiB per-session body limit, strict all-answer address classification, exact-origin policy, and explicit unsupported-protocol denials are fixed acceptance values for this draft. Tests use injected monotonic clock/resolver/socket seams and do not depend on wall-clock time or live DNS.

## 8. Non-goals

- Real Chromium/Playwright or Browserbase production adapter.
- Browser credentials, profile/cookie upload, SecretBroker, login automation, or secret injection.
- Browser frame/screenshot streaming UI, observation surface, Take Control/Return Control, writer grants, or `browser.submit`.
- Enabling browser/network gates, contacting external services, production/test-node deployment, or claiming production readiness.
- Changes to Hub-to-Node transport, arbitrary JavaScript/CDP evaluation, shell, or host access.
