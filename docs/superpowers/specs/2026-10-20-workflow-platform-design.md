# Agent Fleet 工作流平台深度优化设计

日期：2026-10-21。状态：开发规格；F1 与 F2.1–F2.5 已落盘；F3 完整交付闭环和真实试点尚未完成。源码基线与全套导航见[开发入口](../../platform/workflow-platform/README.md)。

## 1. 产品目标与衡量方式

让用户交代一个目标后，系统能够选择获准的执行方式、固定输入、交接产物、核查结果，并在失败或重启后解释进展与继续处理。用户应能回答：正在做什么、在哪执行、等什么、交付哪个版本、依据什么判断完成。

首个场景是代码任务：开发 Agent 产出固定版本，独立评审与测试读取同一版本，用户根据证据接受或退回。下一个场景才扩展到编译→传包→设备测试，以及资料→文稿→媒体合成。

衡量指标包括：通过最终验收的任务比例、每次交付的人工介入次数、返工代数、模型请求/Token、总时长和故障恢复后重复副作用次数。角色数量、工具数量和总测试数量不能单独代表交付能力。

## 2. 现状诊断

| 证据位置 | 已有能力 | 对完整交付的限制 |
|---|---|---|
| hub/domain/platform.py；hub/application/run_worker_service.py | 每个 Run 冻结模型、工作区和一个执行节点 | 缺少跨步骤依赖和输入交接，不能把更改默认节点当作流程调度 |
| tools/platform/tool_broker.py；node_executor.py | 固定工具、作用域、资源租约及节点执行 | 每接一类专业工具仍需显式实现；不是通用 MCP 管理平台 |
| tools/platform/artifacts.py | immutable file、opaque ID、SHA-256；单文件 10 MiB | put_bytes 仅接 PNG，Node 通用工具没有 workspace.artifact；不等于任意文件已能跨节点交接 |
| hub/application/handoff_service.py | 同注册项目内的会话摘要与新任务接力 | 摘要不携带自动同步的源码或通用文件传输，验收标准未结构化 |
| tools/platform/runtime/native.py | 有限模型循环、预算、工具失败和 unknown | 模型 final 结束当前执行，未统一表达业务验证和最终接受 |
| hub/application/legacy_task_bridge.py | 跨 platform/task 库稳定 token 和关联恢复 | 可复用投递思想，但现有“一 Run 关联一旧任务”边界不能直接承载整个多步流程 |
| Muse 工作区、web_agent 工具 | 原生会话、回执、截图、部分委托 | 原生聊天与 Fleet Run 分属不同事实域；sent/confirmed 不代表外部任务完成 |

现有平台已具备不少底层恢复合同。本轮增加协调与交付语义，同时关闭真实运行验收缺口；不把历史计划的未勾选项全部重新开发。

## 3. 三层职责

~~~mermaid
flowchart TB
    U["用户目标、约束与验收"] --> C["WorkContract / 版本化流程模板"]
    C --> W["Workflow 协调器：依赖、预算、输入和证据"]
    W --> N["既有 Native Run"]
    W --> T["既有 Coding Task / CLI adapter"]
    W --> X["固定工具或外部 Agent adapter"]
    N --> D["现有 Command / outbox / Node journal"]
    T --> R["既有 Runner / 隔离工作区"]
    X --> D
    D --> A["节点本地策略与专业软件"]
    A --> P["产物、独立校验和回执"]
    R --> P
    P --> W
    W --> V["任务进度、验证与人工验收"]
~~~

Hub 保持身份、权限、步骤绑定、审计和元数据权威。节点主动领取任务，复验签名、输入和本地权限。模型提出任务方案，确定性协调器判定能否执行。

一个步骤最多绑定一个不可变执行目标。每个子 Run 保持自身配置快照；流程通过不同步骤连接不同节点。重启协调器不会重启已存在的子执行。

## 4. 对象边界

| 对象 | 唯一职责 |
|---|---|
| WorkContract | 描述目标、输入版本、工具与作用域、输出、验证、预算和重试规则 |
| WorkflowDefinition | 版本化有界步骤及依赖；v1 只允许线性链 |
| WorkflowRun | 一个流程实例的持久状态、总预算、定义快照和最终接受状态 |
| WorkflowStepRun | 一个步骤的一代输入与目标绑定；明确当前等待原因 |
| DispatchIntent | 对一个步骤 generation 派发一次逻辑执行的持久意图 |
| Run / Task / Command | 沿用原有执行事实；Workflow 只保存关联与受限投影 |
| ValidationEvidence | 针对固定 subject_digest 的校验证据及其生产者、版本 |
| ArtifactRef | owner/workspace 内不可变文件引用与来源；不能携带远端任意路径 |
| CapabilityDefinition | 管理员授权的工具接口与约束 |
| NodeOffer | 节点当前报告的实现版本、健康及可用容量；不产生授权 |
| AssistantPreset | 提示、工具子集、模型偏好和交付格式；不会增加权限 |

新协调器状态放在既有 platform.db 的附加表。跨旧 task/session 库和外部系统时使用 outbox 与稳定键。保持单 Hub 主机、本地 SQLite WAL；容量测量证明瓶颈后再评估数据库或队列迁移。

## 5. 交付契约与证据

每次交接明确输入、输出和验证方式。代码评审输入需要 repository_id、固定 commit/tree、必要的不可变文件引用及受限任务说明。文本摘要提供背景，不能替代这些输入。

执行、验证、接受分别记录：

- execution_state：程序或 Agent 的执行事实。
- validation_state：针对当前输入和产物的验证结果。
- acceptance_state：最终产物是否由指定主体接受。

流程“执行完成”可以同时显示“校验失败”或“待验收”。只有全部必需步骤完成、必需验证通过且接受条件满足时，派生 delivery_state=delivered。

校验器本身也记录来源信任：固定校验器、Agent 判断、人工决定。结构化 Agent 回复通过 JSON 校验只证明格式正确；评审 Agent 认为“没问题”不会自动成为测试通过事实。

## 6. 首个代码流程

~~~text
需求与约束冻结
  → 开发 Task（获准 worktree）
  → 固定 head/tree + 源码交接包
  → 独立评审（同一 head/tree，受限只读）
  → 固定测试配方（同一 head/tree，隔离执行）
  → 汇总证据与产物
  → 人工接受 / 退回
~~~

v1 使用串行步骤，避免先引入图调度。评审失败会阻断后续放行并展示问题；再次开发通过显式 retry/invalidate 产生新 generation，使旧版本的评审和测试失效。首轮由用户触发返工，后续模板化返工最多两轮且共享预算。

独立评审记录实际 adapter/model 身份与配置，防止 UI 把同一个执行伪装成独立评审。测试执行器依据模板固定的测试配方运行。测试代码同样是不可信代码，必须处于获准 sandbox；worktree 本身不能提供进程、网络或凭据隔离。

人工接受只记录交付决定。合并、推送、部署、外部发布是后续独立动作，仍受原有授权合同控制。

## 7. 对整个项目的优化

### 7.1 可靠性和模块边界

协调器仅推进有界状态，长任务交给已有执行器；不在 Flask handler 中等待模型或文件传输。按 workflow、artifact transfer、capability routing、integration adapter 划分模块，避免继续扩张 agent-runner.py、platform_db.py 和 bootstrap.py。

每个新 repository 负责自己的附加表，但共享同一 DB 路径和事务协调设施。同一事务只能依赖同一连接；不能因文件相同便假设两个 repository 连接之间原子提交。

### 7.2 节点与容量

从“机器名”扩展到“能力、版本、资源和限制”。先过滤 owner/权限、数据位置、平台、能力版本和新鲜度，再按优先级、剩余槽位和稳定 ID 选节点。已派发步骤不能因瞬时负载自动换机。

固定出口、软件许可证、本地数据、ARM64/x86_64 和 GPU 都可以成为明确需求。节点自报地址和标签不能触发 Hub 任意联网，也不能赋予固定出口或许可证权限。

### 7.3 工具和外部系统

增加 MCP adapter 与外部 Agent adapter，各自声明实际支持的提交、查询、取消、恢复和文件导出语义。现有 Muse 原生工作区继续提供原生体验；只有受控投影进入 Workflow，避免复制完整聊天和凭据。

首期只接一个经登记的只读 MCP 和一个已有 CLI adapter。专业软件按真实需求接入，无需先部署工具市场或给所有节点安装相同依赖。

### 7.4 上下文与记忆

上下文采用有界任务摘要、固定输入和产物引用。记忆仍沿用用户显式选择与 revision fence；检索内容作为资料，不改变契约或权限。验证过的结果可以提出记忆候选，仍走既有显式保存入口。

模板、提示和模型选择都版本化。排查失败时能够重建“哪份合同、哪个输入、哪组工具、哪次请求”，而不必依赖无限增长的完整对话。

### 7.5 预算与通知

复用现有 UsageRepository 作为实际请求用量来源，新增流程预算预留与归属，避免子任务重复记账。未知用量保持预留或转为受限未知负债，不直接当零。

普通轮询、续租、健康检查和状态推进不调用模型。通知只面向完成、失败、必要人工动作或重要变化；重复投递使用稳定通知事件键。通知 adapter 未实现时，站内持久事件先可见。

### 7.6 界面与日常可用性

在现有 Assistant/Task 页面显示流程摘要卡：目标、当前步骤、等待原因、验证结果、最终文件和预算。详细视图展现各步骤版本与证据，所有内容经过既有 DOM-safe 渲染和 owner 校验。

提交后显示 queued/accepted 的真实含义。刷新恢复同一 workflow_id 和 after 游标。取消按钮先显示“正在停止”，直到确认实际终止；支持取消不足的外部 Agent 显示“已请求、尚未确认”。

不向普通用户展示租约 token、内部端口、数据库状态或完整协议帧。具体错误使用稳定 reason_code 映射为可操作提示。

## 8. 明确裁决

| 决策 | 原因及重审条件 |
|---|---|
| 增量增加 Workflow 协调层，复用原执行 | 已有租约、签名与 journal 合同可复用；若编排需求超出有界模型再评估框架 |
| v1 线性链，v2 才考虑分支/汇合 | 先验证真实交付与恢复；至少两个用例需要并行汇合后扩展 |
| 保留单 Hub SQLite | 无多 Hub 写入证据；测量锁等待、队列延迟后决策 |
| opaque artifact ID + 完整性 hash | 保持旧 API；相同 hash 不代表跨 owner 可共享或去重授权 |
| MCP 作为工具传输与发现适配 | 目录和权限仍由 Fleet 管理；工具自报注解不是授权 |
| 外部 Agent 确认接收与完成分开 | 网络中断和云机休眠都可能发生，不能自动补发未知副作用 |
| 复用主动出站连接 | 符合现有运维模型，无需重建反向 SSH 控制链 |
| 高风险浏览器及服务能力继续独立准入 | 新工作流不能替代真实浏览器隔离、接管和固定动作验收 |
