# T1.7 Durable Conversation Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with verification checkpoints.

**Goal:** Make the persistent assistant recoverable from its own UI by exposing an owner-scoped, bounded Conversation inbox with recent Run state, while preserving the existing Conversation/Run and single HTTP boundary contracts.

**Architecture:** Add a read-only `GET /api/platform/v1/conversations?limit=` endpoint backed by one bounded SQLite query. The repository returns only conversation metadata, a short last-message preview, and a short latest-Run summary; it does not return owner identity, overrides, client tokens, full messages, event payloads, credentials, or storage paths. The Assistant view renders the list with DOM text nodes and encoded page routes, and keeps the existing explicit `/conversation/<id>` recovery path.

## Constraints

- Preserve the protected primary worktree and all user-owned uncommitted changes.
- Enforce owner isolation in the repository query and operator route.
- Clamp valid limits to `1..100`; malformed or non-positive limits return stable `invalid_limit` `400`.
- Keep list rows bounded: last message preview max 240 characters, latest Run result preview max 500 characters, at most 100 rows.
- Keep `frontend/api/platform.js` as the sole platform HTTP boundary; the view must not call `fetch` or use `innerHTML`.
- Do not add a mutation route, background thread, provider call, node call, or production integration.
