# M2.11 Scheduled HTTP Probe Evidence Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with verification checkpoints.

**Goal:** Connect the versioned HTTP probe contract to an opt-in per-service scheduler with endpoint ownership, SSRF address policy, bounded freshness, and source-isolated Incident recovery.

**Architecture:** Persist one operator-owned `checks.http_probe` policy inside each HTTP service definition. A dedicated scheduler claims `http_probe_sync`, validates the stored endpoint before every request, executes only the exact versioned GET, and sends bounded observations to `IncidentService`, which writes `application_health` evidence and source-specific incidents. The configuration and bootstrap gate remain off by default; loopback is accepted only by an explicit disposable-test override.

**Tech Stack:** Python standard library (`urllib`, `socket`, `ipaddress`), existing SQLite scheduler/service-health/Incident repositories, Flask bootstrap, pytest.

## Global Constraints

- Endpoint policy is read from the persisted service definition; HTTP callers, model output, and node clients cannot override it at probe time.
- Production policy rejects loopback, link-local, private, multicast, unspecified, and reserved resolved addresses; loopback requires an explicit disposable-fixture override.
- Requests are exact `GET` requests to one configured path, with bounded timeout/body/TTL and redirect denial.
- Scheduler and network gates default to `False`; app construction must not create a probe scheduler or open a socket while disabled.
- Probe failures become bounded `unknown` application-health evidence; raw bodies, headers, tokens, endpoint details, and exception text never enter public DTOs or Incident detail.
- Incident fingerprints include `service_id`, source, and rule; repeated unhealthy samples deduplicate and healthy recovery uses the existing recovery streak.
