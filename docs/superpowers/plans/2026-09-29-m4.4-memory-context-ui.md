# M4.4 Memory Context UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Make explicit MemoryItem context usable from `/assistant` while keeping selection bounded, owner-scoped, DOM-safe, and opt-in per turn.

**Architecture:** Add a thin `frontend/api/platform.js` wrapper for owner-scoped memory list/search. Extend the existing native-DOM assistant view with a separate memory picker that renders search results, tracks selected IDs and budgets, and injects `memory_context` only when the user has selected items. The UI never renders memory content into the Run event stream and treats disabled/unavailable memory as a recoverable state.

**Tech Stack:** Static ES modules, existing `platformRequest`/`apiPath` boundary, native DOM APIs, pytest source-contract tests.

## Global Constraints

- Keep the primary worktree untouched; edit only `codex/agent-fleet-platform-m1`.
- Preserve the explicit backend gate: no automatic extraction, search, or prompt injection.
- Use owner-scoped `/api/platform/v1/memory` routes and bounded limits.
- Use `textContent`/DOM node construction only; no `innerHTML` or direct `fetch`.
- Submit `memory_context.enabled=true` only when at least one selected MemoryItem exists; submit IDs, revision fences, and budgets, never memory content.
- Keep `max_items` within 1..20 and `max_bytes` within 256..32768 to match M4.3.
