# M1.9 Deterministic Workspace Post-check Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (or an equivalent inline execution workflow). Steps use checkbox (`- [ ]`) syntax.

**Goal:** Add a durable, fixed read-only post-check for an unknown workspace write so the Hub can record deterministic current-state evidence without replaying the original write or claiming causal proof it does not have.

**Architecture:** An operator requests a post-check for an owner-scoped unknown `tool.workspace.write` command. The Hub derives the original path and expected SHA-256 internally, creates one idempotent `reconcile.workspace.digest` command for the same Node/resource, and waits through the existing Node poll/receipt plane. The Node returns only digest metadata; a matching digest records `workspace_check/confirmed_succeeded` evidence, while a mismatch, read failure, or unknown check records `remains_unknown`. The original command and Run remain `unknown` because the current protocol has no causal write fencing.

**Tech Stack:** Python 3.13, Flask, SQLite/WAL, existing PlatformCommand/CommandRepository/NodeClient/NodeToolExecutor, static assistant UI, pytest. No new dependency, network, or production operation.

## Global Constraints

- Do not replay the original command or send its raw content back to a Node.
- Only `tool.workspace.write` commands are eligible; client input cannot select an arbitrary path or command.
- The post-check command is fixed to `reconcile.workspace.digest` and accepts only `{path}`.
- Digest results contain `path`, `sha256`, and `size`; no file content is returned.
- Owner, Node, workspace resource, and original command relationships are checked server-side.
- A post-check never changes an original `unknown` command or Run state in M1.9.
- Remote execution and provider network gates remain default-off.
