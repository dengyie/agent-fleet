# M1.10 Deterministic Service Inspect Post-check Implementation Plan

**Goal:** Extend the durable post-check plane to ambiguous read-only service.inspect commands without replaying a mutation or trusting client-supplied service parameters.

**Architecture:** An owner requests a post-check for an unknown service.inspect command. The Hub validates the original fixed adapter envelope, reloads the current ServiceDefinition, and requires the node, resource, adapter, target alias, action, and service version to match the original command. It creates one deterministic reconcile.service.inspect command. A Node uses the existing fixed ServiceActionExecutor; a successful bounded inspection records process-state health evidence and post-check matched. Failed or unknown receipts remain unknown. The original command and Run never change state.

**Constraints:** No user executable, argv, alias, or version input; no restart; no raw service output in API, events, or persisted evidence; production action and remote gates remain default-off.
