# T3.4 Assistant Execution Window UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with verification checkpoints.

**Goal:** Connect the existing durable execution-window control plane to `/assistant` so a Run gets a recoverable default execution window with bounded event polling, writer-lease fencing, and close semantics.

**Architecture:** Add an owner-scoped, bounded `GET /execution-windows` collection API keyed optionally by `run_id`, then expose the existing window lifecycle through `frontend/api/platform.js`. The assistant keeps Run and window state separate: Run cancellation remains explicit, window close only closes the UI control-plane resource, and page reload reconstructs the latest window by listing, reconnecting, re-attaching, and reacquiring a writer lease when possible. Window events use their own `after` cursor and only render the allowlisted status/text/notice/input acknowledgement/output contract.

**Tech Stack:** Flask routes, SQLite repository/service, vanilla ES modules, DOM-safe rendering, pytest source/HTTP contracts, Node syntax checks, Obsidian canonical documentation.

## Global Constraints

- Preserve the protected primary worktree and all existing user changes.
- Keep `execution_windows_enabled` default-off and do not add PTY, WebSocket, browser-control, host-command, or real VPS behavior.
- Every window query is owner-scoped; collection limits are bounded and public DTOs never expose tickets, lease tokens, hashes, or metadata secrets.
- The frontend API client is the only HTTP boundary; `assistant.js` must contain no `fetch(` or `innerHTML`.
- Window events are rendered with `textContent`/DOM nodes and a bounded allowlist; arbitrary host input is not accepted.
- Closing a window must never call `cancelRun`; closing the page must not cancel a Run.
- Obsidian updates must use the canonical agent-fleet index, project MOC, and router mounts, followed by `scan-stale-docs`.
