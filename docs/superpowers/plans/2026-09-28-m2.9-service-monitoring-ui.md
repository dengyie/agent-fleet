# M2.9 Service Monitoring View Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with verification checkpoints.

**Goal:** Add a read-only service monitoring view to the static Agent Fleet console so operators can see VPS service health, evidence freshness, and bounded incident summaries beside the main assistant.

**Architecture:** Reuse the existing operator-only `/api/platform/v1/services`, `/services/<id>`, and `/incidents` contracts. Add a small platform API wrapper and a DOM-safe `monitoring` view that renders bounded service rows, health dimensions, evidence timestamps, and incidents; it never calls service actions or Komari sync. Extend the existing shell route/navigation while preserving the legacy fleet, task, session, and assistant views.

**Tech Stack:** Vanilla ES modules, existing `uiIcon` helper, existing `platformRequest` boundary, CSS tokens in `frontend/styles/app.css`, Python static release contract tests, Node syntax checks.

## Global Constraints

- Monitoring is read-only and must not expose restart, approval, Komari sync, or scheduler controls.
- All API calls go through `frontend/api/platform.js` and `platformRequest`; views must not call `fetch` or concatenate `/api` paths.
- Dynamic service names, evidence, and incident text are inserted with `textContent`/DOM nodes, never `innerHTML`.
- Render at most 100 services, 5 evidence rows per service, and 50 incidents; oversized or malformed responses fail closed to a bounded error state.
- Use the existing `uiIcon` symbol helper; do not add a dependency or hand-drawn SVG.
- Keep all platform and mutation gates default-off; no real VPS, Komari endpoint, provider, or deployment is contacted.
