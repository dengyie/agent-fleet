# Workflow workspace bootstrap

**Goal:** Provision the workspace and three conversation bindings required by an existing coding-delivery registration using a repeatable operator CLI.

**Architecture:** `hub.workflow_setup` reads the same bounded registration file and selects one explicit owner/workspace. A scoped infrastructure operation uses original platform validation/schema with one SQLite transaction to create only missing bindings. Default preview opens an existing database read-only and does not initialize stores. Applying uses original `PlatformRepository.init()` then checks all existing bindings before creating any row; conflicting, disabled or archived objects are preserved and rejected. No new HTTP endpoints, identities, privileges, Workflow or execution lifecycle.

**Constraints:** Python3.10, UTF-8/no BOM, protected main worktree, no production mutation/deploy/downloads, no overwriting user data. Existing workspace labels/default nodes and conversation titles/overrides/history remain authoritative. Require an existing absolute local root, exact manifest selection and three distinct valid IDs. No account or Node credential creation.

## Initialization race found during verification

The actual two-process CLI failed on a new temporary database. A diagnostic SQLite connection captured `ALTER TABLE runs ADD COLUMN request_summary TEXT` raising `duplicate column name: request_summary`. The original platform initializer inspected additive columns before acquiring its migration writer transaction. This is a repository migration race, not a CLI binding conflict.

- [x] Add deterministic two-process regressions for both `request_summary` and `fast_digest`. Pause the first process immediately before its additive ALTER, and signal from the second process before requesting its writer transaction, so the corrected lock cannot deadlock the test.
- [x] Move the existing `BEGIN IMMEDIATE` after base `executescript` and before all additive-column inspections. Keep the original migration/version checks, commit and close-on-error behavior. Do not add a CLI-only lock or retry schema errors.
- [x] Verify additive changes roll back on a later migration failure; repeat the original black-box CLI contention on fresh and initialized stores, then run startup, schema/history, backup and boundary regressions on a new frozen source.
