# T3.5 Monitoring Service Actions UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with verification checkpoints.

**Goal:** Extend the existing /monitoring surface with bounded, owner-scoped inspect and approval-backed restart controls while preserving read-only behavior when the action gate is closed.

**Architecture:** Keep all HTTP calls in frontend/api/platform.js. The monitoring view derives action buttons only from the service DTO's allowed_actions, renders a bounded approval card for restart, polls approval state with a fixed attempt budget, and refreshes health after a command is issued. Every dynamic value is inserted as text nodes; action failures remain local notices and never disable service monitoring.

**Tech Stack:** Existing static ES modules, Flask platform APIs, DOM-safe rendering, pytest source contracts, Node syntax checks.

## Global Constraints

- service_actions_enabled remains default-off and no UI action is shown unless the service DTO explicitly allows it.
- inspect is read-only; restart requires an explicit approval decision and never accepts user command arguments.
- Approval polling is bounded and stops on terminal state, request failure, or attempt exhaustion.
- No raw command output, argv, credentials, lease fields, or secret references are rendered.
- Existing service health list/detail behavior remains usable when action endpoints return 404, 409, or network errors.
