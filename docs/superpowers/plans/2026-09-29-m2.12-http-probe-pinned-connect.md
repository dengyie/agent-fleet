# M2.12 Pinned HTTP Probe Connect Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with verification checkpoints.

**Goal:** Bind every network-enabled HTTP probe to the already validated DNS address set so validation and TCP/TLS connection cannot be separated by a hostname re-resolution.

**Architecture:** Keep the operator-owned `checks.http_probe` policy and all default-off gates from M2.11. Resolve the hostname once, classify every returned address, then use a small `http.client` connection adapter that connects directly to those returned socket addresses while preserving the original hostname for the HTTP `Host` header and TLS SNI. Redirects, bounded bodies, error classes, and injected requesters remain unchanged.

**Tech Stack:** Python standard library (`http.client`, `ssl`, `socket`), existing `HttpProbeClient`, pytest, temporary loopback HTTP server.

## Global Constraints

- Never contact a production endpoint, VPS, Komari server, provider, or real DNS name during tests.
- Network, scheduler, and remote execution gates remain off by default.
- The operator-owned URL/path remains the only endpoint source; callers cannot provide a replacement URL.
- Every resolved address must pass the existing loopback/private/link-local/multicast/unspecified/reserved policy before a socket is opened.
- The custom connection must not perform hostname resolution after the policy resolver returns.
- Response bodies, headers, credentials, and exception text remain bounded and absent from public evidence.

- The resolver is called once per real probe request, and no hostname-based fallback exists.
- HTTP and HTTPS paths retain bounded response/error behavior and existing evidence contracts.
- Existing M2.11 gates and regressions remain green.
