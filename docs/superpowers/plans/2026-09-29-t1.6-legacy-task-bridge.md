# T1.6 Legacy Task Bridge Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with verification checkpoints.

**Goal:** Connect an explicit platform Run to the existing legacy TaskService through a durable, retryable outbox and project bounded task results back into the new Run without duplicating legacy coding tasks.

**Architecture:** Add an owner-scoped `legacy_task_links` table to `platform.db`; the row is both the durable bridge outbox and the relation between a Run and one legacy task. Enqueueing atomically moves a queued Run to `waiting_task` and records a sanitized task request. A bridge poll claims pending or linked rows, invokes the existing `TaskService` with a deterministic client token, stores the task/attempt/session relation, and re-reads the task on later polls. Projection events contain only bounded summary, diff metadata, test summary, and file metadata; terminal legacy states move the Run to a terminal state. The two SQLite databases are never treated as one transaction, so retries always reuse the stable token and query the existing task before creating another task.

**Tech Stack:** Python 3.13 standard library, Flask blueprints, existing SQLite repositories, pytest, DOM/API contract tests.

## Global Constraints

- Preserve the protected primary worktree and all user-owned uncommitted changes.
- Legacy task instruction remains a hard 2000-character contract; reject oversized bridge requests instead of silently truncating user intent.
- Use a deterministic client token derived from owner and Run id; never create a second legacy task after a cross-database failure.
- Keep `session_id` optional; only project an already persisted valid session identity and never synthesize a deep link.
- Never send complete conversation text, raw logs, full patches, credentials, storage paths, or unbounded result data into public events.
- Bridge events are private Run events; do not write conversation bodies into the legacy public SSE/event stream.
- Platform, provider, remote-node, service-action, Komari, and production gates remain default-off; tests use disposable local repositories only.

### Task 2: Implement the application bridge and bounded result projection

**Files:**
- Create: `hub/application/legacy_task_bridge.py`
- Modify: `hub/application/run_event_service.py`
- Test: `tests/test_legacy_task_bridge.py`

**Interfaces:**
- `LegacyTaskBridge.enqueue(owner_id, run_id, request)` validates the legacy task shape and hard 2000-character instruction limit before writing the outbox.
- `LegacyTaskBridge.process_once(owner_id)` claims one link, calls `TaskService.create` using a stable generated client token, refreshes the current legacy task, and returns a bounded link DTO.
- `LegacyTaskBridge.get(owner_id, run_id, refresh=True)` returns the current link projection without exposing task storage internals.
- The projection contains `task_id`, current `attempt_id`, optional existing `session_id`, task state, `summary` (max 2000 chars), diff metadata, allowlisted test summary, and bounded result-file metadata.

Assert a transient create failure leaves a retryable outbox row, the next poll creates one task with the same deterministic token, pause/continue updates `attempt_id`, and a completed task projects summary/diff/tests/files into one private Run event and a terminal Run state.

- [x] **Step 2: Implement validation and deterministic token derivation**

Validate with the existing task domain validator, reject instruction length over 2000 before enqueue, and derive `legacy-run-<sha256(owner + NUL + run_id)>` as the only client token used for retries.

- [x] **Step 3: Implement claim processing and retry classification**

Call `TaskService.create` only after the durable row is claimed. On success, read the task through `TaskService.get` and the repository for the current attempt. Retry storage/unavailable errors by releasing the claim; mark malformed/permanent policy errors failed with a bounded error event. Every later poll re-reads the same task id and never calls create with another token.

- [x] **Step 4: Implement bounded projection and terminal mapping**

Project only summary, `diff_stat`/patch metadata, allowlisted test fields, and at most 50 file metadata rows. Map queued/leased/running/paused to `waiting_task`, succeeded to `succeeded`, failed/expired to `failed`, and cancelled to `cancelled`. Emit `legacy_task_update` only when the projection changes; use the existing repository transaction to prevent stale writes.
